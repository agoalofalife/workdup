# Installation

workdup is a single binary with no runtime dependencies beyond `ca-certificates` — SQLite is compiled in, and TLS uses rustls rather than system OpenSSL. There is nothing to provision but the binary, a config file, and a writable directory for the database.

| Path                                  | Use it when                                                                                |
| ------------------------------------- | ------------------------------------------------------------------------------------------ |
| [Install script](#install-script)     | Developer machines and CI runners — one command, verifies checksums                        |
| [Prebuilt binary](#prebuilt-binaries) | You want to inspect what you run before running it, or you don't pipe to a shell           |
| [From source](#build-from-source)     | Your platform isn't published, your glibc is older than the runners', or you're developing |
| [Container](#container)               | Kubernetes, or local evaluation with `docker compose`                                      |

## Install script

```bash
curl -fsSL https://raw.githubusercontent.com/agoalofalife/workdup/main/install.sh | sh
```

The script detects your OS and architecture, downloads the matching release tarball, and installs `workdup` into `/usr/local/bin`.

Configure it with environment variables:

| Variable              | Default                | Purpose                                                                                |
| --------------------- | ---------------------- | -------------------------------------------------------------------------------------- |
| `WORKDUP_VERSION`     | `latest`               | Tag to install, e.g. `v0.2.0`. `latest` is resolved from the GitHub releases API       |
| `WORKDUP_INSTALL_DIR` | `/usr/local/bin`       | Where the binary lands. If it isn't writable, the script re-runs the move under `sudo` |
| `WORKDUP_REPO`        | `agoalofalife/workdup` | Source repository — for forks and mirrors                                              |

```bash
# a specific version, into a user-writable directory (no sudo)
curl -fsSL https://raw.githubusercontent.com/agoalofalife/workdup/main/install.sh \
  | WORKDUP_VERSION=v0.2.0 WORKDUP_INSTALL_DIR="$HOME/.local/bin" sh
```

It needs `curl` and `tar` on `PATH` and fails immediately with a clear message if either is missing. On unsupported platforms it exits rather than guessing — see the target table below.

## Prebuilt binaries

Four targets are published per release, as `.tar.gz` archives each containing a single `workdup` executable:

| Target                      | Platform                |
| --------------------------- | ----------------------- |
| `x86_64-unknown-linux-gnu`  | Linux, Intel/AMD 64-bit |
| `aarch64-unknown-linux-gnu` | Linux, ARM64            |
| `x86_64-apple-darwin`       | macOS, Intel            |
| `aarch64-apple-darwin`      | macOS, Apple silicon    |

Assets are named `workdup-<tag>-<target>.tar.gz` — for example `workdup-v0.1.0-aarch64-apple-darwin.tar.gz`.

No Windows build, and no static Linux build

There is no Windows target and no musl build. The Linux binaries link against glibc and are compiled on GitHub's Ubuntu runners, so a distribution with an older glibc than the runner's will refuse to load them. On older Linux, [build from source](#build-from-source) or run the [container](#container).

Download the archive and `SHA256SUMS` from the [releases page](https://github.com/agoalofalife/workdup/releases), then verify before you extract:

```bash
sha256sum --check --ignore-missing SHA256SUMS
```

```bash
shasum -a 256 --check --ignore-missing SHA256SUMS
```

Both print `OK` for each matched file. Then install it:

```bash
tar -xzf workdup-v0.1.0-aarch64-apple-darwin.tar.gz
chmod +x workdup
sudo mv workdup /usr/local/bin/
```

## Build from source

This section was generated by AI

The dependency lists and commands below were derived from [`release.yml`](https://github.com/agoalofalife/workdup/blob/main/.github/workflows/release.yml) by an AI assistant rather than verified by hand on a clean machine. They match what CI installs. If a step fails on your platform, please open an issue.

The build needs three things beyond a Rust toolchain, and they are the step people get wrong: `protoc` to compile the Temporal protobuf definitions, `cmake` because `aws-lc-rs` builds its native crypto with it, and a working C toolchain. SQLite and TLS are compiled in, so you do **not** need `libsqlite3-dev` or `libssl-dev`.

```bash
sudo apt-get update
sudo apt-get install -y --no-install-recommends \
  build-essential pkg-config protobuf-compiler libprotobuf-dev cmake
```

```bash
brew install protobuf cmake
```

Then build with the lockfile pinned, which is what the release workflow does:

```bash
git clone https://github.com/agoalofalife/workdup.git
cd workdup
cargo build --release --locked
```

The binary lands at `target/release/workdup`. Copy it onto your `PATH` if you want it available globally.

## Container

Build the image from the repository:

```bash
docker build -t workdup:local .
```

This repository does not publish a container image — build your own from the `Dockerfile` above.

The image is a two-stage build on `debian:bookworm-slim` and hardcodes a default command, so it runs with no arguments:

| Property        | Value                                                               |
| --------------- | ------------------------------------------------------------------- |
| Entrypoint      | `workdup`                                                           |
| Default command | `--config /app/workdup.toml run`                                    |
| Config path     | `/app/workdup.toml` — mount your config here                        |
| Data directory  | `/app/data` — **mount a volume or the database is lost on restart** |
| Exposed ports   | `8000` (REST API + app metrics), `9000` (Temporal SDK gRPC metrics) |

```bash
docker run --rm \
  -v "$PWD/workdup.toml:/app/workdup.toml:ro" \
  -v workdup-data:/app/data \
  -p 8000:8000 -p 9000:9000 \
  workdup:local
```

## First run

### Working directory matters

workdup resolves three paths relative to the **current working directory**, so where you launch it changes how it behaves:

| Path                | Behaviour                                                                                                    |
| ------------------- | ------------------------------------------------------------------------------------------------------------ |
| `./data/workdup.db` | The SQLite database. Hardcoded and **not configurable**; the `data/` directory is created on demand by `run` |
| `.env`              | Loaded on startup if present, before the config is read                                                      |
| `workdup.toml`      | The default `--config` value, a relative path                                                                |

Launch from a different directory and you get a different — empty — database. For a systemd unit or any supervisor, set the working directory explicitly rather than relying on inheritance:

```ini
[Service]
WorkingDirectory=/var/lib/workdup
ExecStart=/usr/local/bin/workdup --config /etc/workdup/workdup.toml run
```

### A minimal config

The smallest config that starts is one namespace with a host. Everything else has a default:

workdup.toml

```toml
[[namespaces]]
name = "my-namespace"
host = "my-namespace.abcde.tmprl.cloud:7233"
```

Defaults you get for free: `scan_interval` `1h`, `cleanup_interval` `1d`, query `ExecutionStatus = 'Running'`, API port `8000`, Temporal metrics port `9000`. See [Configuration](https://agoalofalife.github.io/workdup/dev/configuration/index.md) for the full reference, and [Environment variables](https://agoalofalife.github.io/workdup/dev/environment-variables/index.md) for credentials — those belong in the environment rather than in the file.

### Check it

Use `--version` to confirm the binary runs, and `validate` to confirm the config is real:

```console
$ workdup --version
workdup 0.2.0

$ workdup --config workdup.toml validate
ok: 2 namespace(s)
```

`validate` loads the file, expands `${VAR}` references, applies any `WORKDUP__*` overrides, and checks that at least one namespace is defined, that no name is duplicated, that no host is empty, and that **every TLS certificate path exists as a real file**. It does not dial Temporal and it does not touch the database — nothing is created, so it is safe to run anywhere. That is what makes it useful as a CI check or a Kubernetes init container.

Once `validate` passes, start the daemon:

```bash
workdup run
```

## Local observability stack

The repository ships a Compose stack that runs workdup with Prometheus and Grafana, with the dashboard already provisioned — the fastest way to see the [metrics](https://agoalofalife.github.io/workdup/dev/metrics/index.md) in context:

```bash
docker compose up --build
```

| Service                | URL                             | Notes                                                                                      |
| ---------------------- | ------------------------------- | ------------------------------------------------------------------------------------------ |
| Grafana                | <http://localhost:3000>         | Anonymous admin; dashboard auto-provisioned under **Dashboards → workdup — Observability** |
| Prometheus             | <http://localhost:9090>         | Check **Status → Targets** are `UP`                                                        |
| REST API + app metrics | <http://localhost:8000>         | `/metrics`, `/healthz`, `/readyz`, `/stats`, `/unique-workflows`                           |
| Temporal SDK metrics   | <http://localhost:9000/metrics> | gRPC client metrics                                                                        |
